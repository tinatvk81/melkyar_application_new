# سامانه‌ی مدیریت فایل‌های ملکی (دسکتاپ، چندکاربره)

معماری: **PostgreSQL** (فقط روی سرور مرکزی دفتر) ← **FastAPI** (لایه‌ی API، روی همان سرور) ← **PySide6** (اپ دسکتاپ روی سیستم هر مشاور، فقط با HTTP به سرور وصل می‌شود، هیچ رمز دیتابیسی روی لپ‌تاپ مشاور ذخیره نمی‌شود).

جزئیات کامل تصمیمات و دلایل در فایل `roadmap-v2.md` است. این فایل فقط دستورهای اجرایی است.

---

## ۱. پیش‌نیازها (روی سیستمی که سرور روی آن نصب می‌شود)

1. Python 3.11 یا بالاتر
2. PostgreSQL 15+ (نصب و در حال اجرا، فقط روی `localhost`)
3. ساخت دیتابیس و کاربر اختصاصی در PostgreSQL:
   ```sql
   CREATE DATABASE realestate;
   CREATE USER realestate_app WITH ENCRYPTED PASSWORD 'یک-رمز-قوی';
   GRANT ALL PRIVILEGES ON DATABASE realestate TO realestate_app;
   ```

## ۲. ساخت venv خصوصی برای سرور

```bash
cd realestate-app/server
python -m venv venv

# فعال‌سازی venv:
# ویندوز (cmd):
venv\Scripts\activate.bat
# ویندوز (PowerShell):
venv\Scripts\Activate.ps1
# لینوکس/مک:
source venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt
```

سپس فایل `.env.example` را کپی کنید و مقداردهی کنید:
```bash
cp .env.example .env
# .env را باز کنید و POSTGRES_PASSWORD و SECRET_KEY واقعی را بگذارید
```

ساخت جدول‌های دیتابیس با Alembic (این مرحله را واقعاً روی یک PostgreSQL واقعی تست
کردم — هم upgrade و هم downgrade درست کار می‌کنند، شامل تایپ‌های Enum پستگرس):
```bash
alembic upgrade head
```
هر بار که مدل‌ها (`app/models/*.py`) را تغییر دادید، یک migration جدید بسازید:
```bash
alembic revision --autogenerate -m "توضیح کوتاه تغییر"
alembic upgrade head
```

ساخت اولین کاربر مدیر (بعد از `alembic upgrade head`):
```bash
python scripts/init_admin.py
```

اجرای سرور (روی شبکه‌ی محلی دفتر در دسترس است، نه از اینترنت بیرون):
```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

مستندات خودکار API (برای تست سریع endpointها در مرورگر همان سرور):
`http://localhost:8000/docs`

## ۳. ساخت venv خصوصی برای کلاینت (روی سیستم توسعه، یا هر لپ‌تاپ مشاور)

```bash
cd realestate-app/client
python -m venv venv
venv\Scripts\activate.bat        # یا معادل آن طبق بخش بالا

pip install --upgrade pip
pip install -r requirements.txt
```

قبل از اجرا، آدرس سرور را تنظیم کنید — دو راه دارید:
- **از داخل خودِ برنامه (ساده‌تر):** برنامه را اجرا کنید، در پنجره‌ی ورود دکمه‌ی
  «تنظیمات اتصال» را بزنید، آدرس را وارد کنید، «تست اتصال» بزنید، بعد «ذخیره».
- **یا مستقیم فایل تنظیمات را ویرایش کنید:** بعد از اولین اجرا، یک فایل
  `settings.json` کنار `main.py` ساخته می‌شود؛ آن را با هر ویرایشگر متنی باز
  کنید و `server_url` را عوض کنید — نیازی به تغییر کد یا نصب مجدد نیست.

(اگر می‌خواهید مقدار پیش‌فرض اولیه برای همه‌ی نصب‌های جدید فرق کند،
`client/config.py` را هم می‌توانید عوض کنید، ولی این فقط اولین‌بار قبل از
ساخته‌شدن `settings.json` استفاده می‌شود.)

فونت فارسی Vazirmatn را دانلود کنید و در مسیر زیر بگذارید:
```
client/resources/fonts/Vazirmatn-Regular.ttf
```
(از https://github.com/rastikerdar/vazirmatn — بخش Releases، فایل‌های ttf)

اجرای برنامه:
```bash
python main.py
```

## ۴. ساخت نصب‌کننده‌ی exe برای پخش به مشاوران (فاز بعدی)

```bash
cd realestate-app/client
pip install -r requirements-dev.txt
pyinstaller --noconsole --onefile --name RealEstateApp main.py
```
فایل خروجی در `dist/RealEstateApp.exe` است. این فایل را در پوشه‌ی
`server/static_installers/` روی سرور کپی کنید تا مکانیزم آپدیت خودکار
(`GET /version`) بتواند آن را به کلاینت‌های قدیمی‌تر معرفی کند.

## ۵. بک‌آپ خودکار (روی سیستم سرور)

```bash
cd realestate-app/server
venv\Scripts\activate.bat
python scripts/backup.py
```
این را در Windows Task Scheduler به‌صورت روزانه (مثلاً ساعت ۳ بامداد) زمان‌بندی کنید.
جزئیات کامل استراتژی در کامنت‌های بالای همان فایل و در `roadmap-v2.md` بخش ۸ است.

## ۷. وضعیت فعلی این اسکلت (چه چیزی کار می‌کند، چه چیزی باقی مانده)

**آماده و قابل اجرا:**
- ورود با نام کاربری/رمز (JWT)، تفکیک نقش مدیر/مشاور
- فهرست فایل‌ها (با فیلتر خودکار سمت سرور: مشاور فقط فایل خودش)
- **فرم کامل افزودن/ویرایش فایل ملکی** (`client/ui/property_form.py`): فیلدهای مشترک
  + فیلدهای اختصاصی هر نوع معامله (فروش/پیش‌خرید/اجاره/رهن‌کامل) که با انتخاب
  نوع معامله خودکار عوض می‌شوند، همراه با **تاریخ شمسی** برای تاریخ تحویل/پایان قرارداد
  (`client/ui/jalali_date_edit.py`)
- دکمه‌های افزودن/ویرایش/غیرفعال‌سازی فایل + دابل‌کلیک روی ردیف برای ویرایش سریع
- تب قراردادهای رو‌به‌اتمام (ماژول یادآوری)
- مدیریت کاربران برای مدیر (`client/ui/user_form_dialog.py` + بخش `UserManagementTab`):
  ساخت حساب مشاور/مدیر جدید، غیرفعال/فعال کردن با یک دکمه (متن دکمه خودکار بین این دو حالت
  عوض می‌شود)، ریست رمز عبور — همه با ابطال فوری توکن‌های نشست باز آن کاربر (طبق تصمیم امنیتی
  بخش ۴ roadmap-v2.md)
- **گالری تصاویر** (`server/app/api/routes/property_images.py` + `client/ui/property_gallery_dialog.py`):
  آپلود چند عکس هم‌زمان، نمایش thumbnail، حذف تک‌تک عکس‌ها. عکس‌ها روی دیسک سرور در
  `server/media/properties/{id}/` با نام تصادفی (uuid) ذخیره می‌شوند (نه در دیتابیس، تا حجم
  دیتابیس و بک‌آپ‌گیری سنگین نشود). هر درخواست دیدن/حذف عکس همان قانون دسترسی مشاور/مدیر
  فایل ملکی مربوطه را چک می‌کند (بر خلاف یک پوشه‌ی static عمومی که هرکسی لینک را داشته باشد
  می‌تواند ببیند) — این پوشه از قبل در `scripts/backup.py` لحاظ شده است.
- **گزارش‌ها و خروجی PDF/اکسل** (`server/app/services/pdf_export.py`, `excel_export.py`,
  `server/app/api/routes/reports.py`): خروجی PDF/اکسل از فهرست فایل‌های قابل‌مشاهده‌ی کاربر
  (با همان محدودیت دسترسی مشاور/مدیر)، و برای مدیر یک تب «گزارش عملکرد مشاوران» با تعداد فایل
  هر مشاور به تفکیک نوع معامله + خروجی PDF همان گزارش. **PDF فارسی به‌درستی رندر می‌شود**
  (حروف به‌هم‌چسبیده و راست‌به‌چپ) چون از `arabic-reshaper` + `python-bidi` + فونت Vazirmatn
  استفاده شده — این ترکیب را واقعاً تست کردم و خروجی را به تصویر تبدیل کردم تا مطمئن شوم درست
  چاپ می‌شود.

**نکته‌ی فونت:** فایل واقعی `Vazirmatn-Regular.ttf` (رایگان، مجوز SIL OFL) از قبل در
`client/resources/fonts/` و `server/app/resources/fonts/` قرار داده شده — دیگر نیازی به دانلود
دستی نیست.
- **Import اکسل** (`server/app/services/excel_import_service.py` + `client/ui/import_excel_dialog.py`):
  دانلود قالب نمونه با ۴ شیت (فروش/پیش‌خرید/اجاره/رهن_کامل) + شیت راهنما، آپلود فایل تکمیل‌شده،
  گزارش دقیق ردیف‌به‌ردیف خطاها (با شماره‌ی ردیف واقعی در اکسل) بدون متوقف‌شدن کل Import —
  تست شده با داده‌ی واقعی و ردیف‌های خراب عمدی، هم مسیر موفق و هم مسیر خطا درست کار می‌کند.
- راست‌به‌چپ کامل + بارگذاری فونت فارسی
- مکانیزم چک نسخه‌ی جدید
- اسکریپت بک‌آپ با چرخش روزانه/هفتگی/ماهانه

- **Alembic migration** (`server/alembic/`): جدول‌ها دیگر با `create_all` ساخته نمی‌شوند.
  این را واقعاً روی یک PostgreSQL واقعی نصب کردم و تست کردم — `alembic upgrade head` تمام
  ۴ جدول (users, properties, activity_logs, property_images) + ایندکس‌ها را درست می‌سازد،
  و `alembic downgrade base` هم درست پاک می‌کند (شامل حذف صریح تایپ‌های Enum پستگرس که
  Alembic به‌طور پیش‌فرض فراموش می‌کند حذف کند — این باگ را واقعاً گرفتم و در migration
  اولیه دستی درستش کردم).
- **رفع یک باگ واقعی سازگاری نسخه:** ترکیب `passlib==1.7.4` با نسخه‌های جدید `bcrypt` (۴.۱+)
  خطای «password cannot be longer than 72 bytes» می‌دهد چون passlib به یک ویژگی داخلی
  bcrypt نیاز دارد که در نسخه‌های جدید حذف شده. در `requirements.txt` نسخه‌ی `bcrypt==4.0.1`
  صریحاً پین شده تا این مشکل پیش نیاید (این را هم واقعاً روی سیستم بازتولید و رفع کردم).

**باقی‌مانده برای فازهای بعدی (طبق roadmap-v2.md):** هیچ‌کدام — همه‌ی موارد این roadmap
پیاده‌سازی و تست شدند. آخرین مورد هم همین بود:

- **پنل فیلتر پیشرفته** (`client/ui/property_filter_panel.py` + `apply_filters()` در `properties.py`):
  فیلتر بر اساس شهر، منطقه، نوع معامله، بازه‌ی متراژ، حداقل تعداد اتاق، آسانسور/پارکینگ،
  و **بازه‌ی قیمت** — با وجود این‌که قیمت داخل ستون JSONB و با اسم متفاوت برای هر نوع معامله
  ذخیره شده (`price`/`total_price`/`deposit_full`/`monthly_rent`)، یک عبارت SQL با
  `COALESCE` ساخته شده که همه‌ی این‌ها را به‌عنوان «مبلغ» در نظر می‌گیرد. همین فیلترها را
  می‌توان مستقیم به خروجی PDF/اکسل هم پاس داد (یک تابع `apply_filters` مشترک بین فهرست و
  export استفاده می‌شود) تا خروجی همیشه دقیقاً با چیزی که کاربر فیلتر کرده یکی باشد.

**باگ‌های واقعی که در این فاز پیدا و رفع کردم (با تست مستقیم روی PostgreSQL و FastAPI واقعی):**
- فیلتر بازه‌ی قیمت روی JSONB را با داده‌ی واقعی تست کردم (چند فایل با مبلغ‌های مختلف ساختم و
  چک کردم فیلتر `min_price`/`max_price` درست کار می‌کند).
- **باگ جدی در Content-Disposition:** اسم فایل‌های دانلودی (PDF/اکسل) اولش فارسی بود
  (مثلاً `فهرست-فایل-ها.pdf`)، ولی هدرهای HTTP فقط کاراکترهای Latin-1 قبول می‌کنند و این باعث
  کرش کامل سرور (خطای ۵۰۰) هنگام دانلود هر خروجی می‌شد. این را با تست واقعی HTTP گرفتم و اسم
  فایل‌های دانلودی را انگلیسی کردم (محتوای داخل فایل همچنان کاملاً فارسی است، فقط اسم فایل).

## نسخه‌ی ۳ (roadmap-v3.md) — در حال پیاده‌سازی

**۱. صفحه‌بندی واقعی فهرست فایل‌ها ✅ (انجام شد):**
نسخه‌ی قبلی یک `.limit(500)` هاردکد داشت که در مقیاس ۱۰٬۰۰۰+ فایل باعث می‌شد
فایل‌های بعد از ۵۰۰ اُم بی‌صدا از دید مدیر پنهان بمانند — نه خطایی، نه پیامی.
حالا `GET /properties/` پارامترهای `page` و `page_size` (حداکثر ۲۰۰) می‌پذیرد
و `total`, `total_pages` را هم برمی‌گرداند. **این را با ۶۵۰ رکورد واقعی روی
PostgreSQL تست کردم:** با `page_size` پیش‌فرض ۵۰، دقیقاً ۱۳ صفحه محاسبه شد،
صفحه‌ی آخر درست ۵۰ آیتم داد، و درخواست `page_size=1000` درست در سقف ۲۰۰ محدود
شد. کلاینت (`PropertyListTab`) حالا دکمه‌های «صفحه‌ی قبل/بعد» و برچسب
«صفحه X از Y — تعداد کل: N» دارد؛ تغییر فیلتر خودکار به صفحه‌ی ۱ برمی‌گردد.

**۲. آرشیو و بازگردانی فایل‌های غیرفعال‌شده ✅ (انجام شد):**
قبلاً دکمه‌ی «غیرفعال کردن» بود ولی هیچ راهی برای دیدن یا برگرداندن فایل
غیرفعال‌شده نبود. حالا `GET /properties/archived` (با همان منطق صفحه‌بندی و
همان قانون دسترسی مشاور/مدیر) فهرست فایل‌های غیرفعال را می‌دهد، و
`POST /properties/{id}/reactivate` آن را برمی‌گرداند. کلاینت یک دیالوگ «آرشیو
فایل‌های غیرفعال» دارد با دکمه‌ی «بازگردانی». **این را با یک چرخه‌ی کامل واقعی
تست کردم:** ساخت فایل → دیدنش در فهرست فعال → غیرفعال کردن → ناپدید شدن از
فعال و ظاهر شدن در آرشیو → بازگردانی → ظاهر شدن دوباره در فعال و ناپدید شدن از
آرشیو — همه‌ی این مراحل روی PostgreSQL واقعی از طریق HTTP تست شد.

**۳. ثبت واقعی تاریخچه‌ی فعالیت‌ها (ActivityLog) ✅ (انجام شد):**
مدل `ActivityLog` از فاز اول ساخته شده بود ولی هیچ‌جا استفاده نمی‌شد. حالا یک
سرویس مشترک (`app/services/activity_log_service.py`) در تمام نقاط کلیدی صدا
زده می‌شود: ثبت/ویرایش/غیرفعال‌سازی/بازگردانی فایل، ورود کاربر، ساخت/غیرفعال/
فعال‌سازی/ریست‌رمز کاربر، ایمپورت اکسل، آپلود/حذف عکس. یک endpoint جدید
(`GET /activity-logs/`, فقط مدیر) با فیلتر نوع/بازه‌ی زمانی و صفحه‌بندی، و یک
تب جدید «تاریخچه‌ی فعالیت‌ها» در کلاینت. **این را با یک سناریوی کامل واقعی
تست کردم:** ثبت فایل → ویرایش → غیرفعال‌سازی → بازگردانی → ساخت کاربر جدید،
و بعد فهرست لاگ‌ها را گرفتم — هر ۶ عملیات با کاربر و زمان و جزئیات درست ثبت
شده بودند؛ فیلتر `entity_type=user` درست ۳ مورد را برگرداند، و دسترسی مشاور
(غیرمدیر) با خطای ۴۰۳ درست مسدود شد.

**۴. جستجوی آزاد (کلیدواژه) ✅ (انجام شد):**
یک جعبه‌ی جستجوی ساده در پنل فیلتر اضافه شد که هم‌زمان روی ۶ ستون می‌گردد:
شهر، منطقه، آدرس، توضیحات، نام مالک، تلفن مالک (`ILIKE` با `OR` در
`apply_filters`، در `properties.py`). با فیلترهای دیگر (مثل نوع معامله) هم
ترکیب می‌شود (AND) و در خروجی PDF/اکسل هم اعمال می‌شود. **این را با ۳ فایل
واقعی با متن‌های متفاوت تست کردم:** جستجوی «ولیعصر» فقط آدرس را پیدا کرد،
جستجوی «احمد» هر دو مالک «احمد رضایی» و «مریم احمدی» را همزمان پیدا کرد،
جستجوی شماره تلفن هر دو فایل با آن شماره را پیدا کرد، جستجو در توضیحات هم کار
کرد، و ترکیب جستجو + فیلتر نوع معامله هم درست AND شد.

**۵. مرتب‌سازی فهرست ✅ (انجام شد):**
دو دراپ‌داون «مرتب‌سازی بر اساس» (تاریخ ثبت/قیمت/متراژ/تاریخ پایان قرارداد) و
«نزولی/صعودی» به پنل فیلتر اضافه شد که با تغییرشان بلافاصله (بدون نیاز به زدن
دکمه‌ی اعمال فیلتر) فهرست را دوباره مرتب می‌کنند. مرتب‌سازی بر اساس قیمت از
همان عبارت `COALESCE` مشترک استفاده می‌کند (چون قیمت برای انواع معامله در
فیلدهای متفاوتی ذخیره شده) و به همین دلیل با فیلتر بازه‌ی قیمت هم‌خوان است.
**با ۵ فایل واقعی با قیمت/متراژ/تاریخ متفاوت تست کردم:** مرتب‌سازی صعودی/نزولی
بر اساس قیمت دقیقاً با ترتیب واقعی مبلغ‌ها (even برای اجاره که «قیمت» در
واقع `monthly_rent` است) مطابقت داشت؛ مرتب‌سازی بر اساس متراژ درست بود؛
مرتب‌سازی بر اساس تاریخ پایان قرارداد فایل‌های بدون این تاریخ (مثل فروش) را
درست در انتها قرار داد (رفتار NULLS LAST پیش‌فرض پستگرس).

**۶. تنظیمات سرور در فایل خارجی قابل‌ویرایش ✅ (انجام شد):**
قبلاً `SERVER_URL` داخل `client/config.py` هاردکد بود — یعنی تغییر IP سرور
دفتر یعنی ساخت دوباره‌ی exe و نصب مجدد روی همه‌ی لپ‌تاپ‌ها. حالا
`settings_manager.py` یک `settings.json` کنار خودِ فایل اجرایی (یا کنار
`main.py` در حالت توسعه) می‌سازد و از آن می‌خواند؛ `config.py` فقط «مقدار
پیش‌فرض اولیه» را نگه می‌دارد. علاوه بر این، یک دکمه‌ی «تنظیمات اتصال» در
پنجره‌ی ورود اضافه شد که همان کار را از داخل خودِ برنامه (بدون نیاز به باز
کردن فایل با Notepad) با یک دکمه‌ی «تست اتصال» (بدون نیاز به لاگین، فقط
`/health`) انجام می‌دهد. **این را با ۳ سناریوی واقعی تست کردم:** اولین اجرا
(بدون فایل settings.json) درست فایل را با مقدار پیش‌فرض می‌سازد؛ تغییر و
ذخیره‌ی آدرس جدید هم در فایل هم در نمونه‌ی زنده‌ی `ApiClient` درست منعکس
می‌شود؛ و اگر فایل settings.json به هر دلیلی خراب/ناخوانا شود، برنامه کرش
نمی‌کند و بی‌صدا به مقدار پیش‌فرض برمی‌گردد.

**۷. مدیریت خودکار انقضای نشست ✅ (انجام شد):**
قبلاً وقتی توکن JWT منقضی می‌شد یا اعتبارش از بین می‌رفت (مثلاً مدیر رمز کاربر
را ریست کرده یا حسابش را غیرفعال کرده)، کاربر در هر صفحه‌ای که بود فقط یک
خطای گنگ می‌دید. حالا یک ماژول مرکزی (`client/session.py`) اضافه شد: به‌جای
`QMessageBox` مستقیم بعد از `except ApiError`، همه‌جا (۲۰ نقطه در ۶ فایل)
از تابع مشترک `handle_api_error()` استفاده می‌کنند که اگر خطا واقعاً کد ۴۰۱
باشد، به‌جای پیام محلی، کاربر را با یک پیام روشن («نشست شما پایان یافته...»)
به صفحه‌ی ورود برمی‌گرداند — و اگر چند درخواست هم‌زمان ۴۰۱ بگیرند، فقط یک‌بار
این پیام نشان داده می‌شود، نه چندبار. تبدیل این ۲۰ نقطه با یک اسکریپت خودکار
(نه دستی) انجام شد تا خطای انسانی در کپی/پیست پیش نیاید؛ دو مورد مشابه که در
واقع `except ValueError` بودند (اعتبارسنجی محلی، نه خطای شبکه) به‌درستی
دست‌نخورده باقی ماندند، و `login_window.py` هم عمداً تغییر نکرد چون آن‌جا
۴۰۱ یعنی «رمز اشتباه»، نه «نشست منقضی».

**تست واقعی که انجام دادم:** یک مشاور تست وارد شد و یک توکن گرفت؛ سپس با یک
کلاینت مدیر جداگانه، رمز همان مشاور را ریست کردم (که `token_version` را عوض
می‌کند)؛ بعد با همان توکن قدیمی مشاور دوباره درخواست دادم — سرور درست با کد
۴۰۱ و پیام «نشست شما نامعتبر است» رد کرد. جداگانه هم منطق `session.py` را با
PySide6 واقعی (به‌صورت headless/offscreen) تست کردم: خطای معمولی درست دیالوگ
نشان می‌دهد بدون فعال‌سازی انقضای نشست؛ خطای ۴۰۱ درست callback را فعال
می‌کند بدون دیالوگ محلی؛ چند خطای ۴۰۱ پشت‌سرهم فقط یک‌بار trigger می‌شوند؛ و
بعد از یک ورود موفق دوباره (`reset_session_expired_flag`)، مکانیزم دوباره
برای دفعه‌ی بعد آماده می‌شود.

**۸. قفل هم‌زمان (Optimistic Locking) ✅ (انجام شد):**
قبلاً اگر دو مشاور هم‌زمان یک فایل را ویرایش می‌کردند، آخرین ذخیره بی‌سروصدا
تغییرات دیگری را رونویسی می‌کرد. حالا مدل `Property` یک ستون `version` دارد
که با هر ویرایش موفق `+۱` می‌شود؛ کلاینت نسخه‌ای را که خوانده در درخواست
ویرایش برمی‌گرداند، و اگر با نسخه‌ی فعلی دیتابیس فرق داشته باشد، سرور با کد
۴۰۹ رد می‌کند (به‌جای رونویسی بی‌صدا). فرم ویرایش کلاینت این حالت را جدا از
خطاهای دیگر تشخیص می‌دهد و به‌جای پیام گنگ، می‌گوید «این فایل توسط شخص دیگری
تغییر کرده، فایل را دوباره باز کنید» و فهرست پشت آن را هم تازه می‌کند.

**تست واقعی که انجام دادم (شبیه‌سازی دو کاربر هم‌زمان):** یک فایل ساختم
(نسخه‌ی ۱)، هر دو «کاربر» همان نسخه را خواندند، کاربر A ذخیره کرد (نسخه شد ۲)،
کاربر B با نسخه‌ی قدیمی (۱) سعی کرد ذخیره کند — سرور با ۴۰۹ رد کرد و پیام
درست را برگرداند. بررسی نهایی دیتابیس تایید کرد که آدرس نهایی همان چیزی است
که A ذخیره کرده، نه B، و نسخه درست روی ۲ مانده است. همچنین migration این
ستون را روی یک ردیف واقعاً از‌قبل‌موجود (شبیه‌سازی دیتابیس تولید) تست کردم:
مقدار پیش‌فرض ۱ درست backfill شد، و downgrade/upgrade هم تمیز کار کرد.

**۹. جلوگیری از ثبت تکراری در Import اکسل ✅ (انجام شد):**
تشخیص تکراری در دو سطح انجام می‌شود: ۱) در برابر فایل‌های از‌قبل‌موجود در
دیتابیس (همان مشاور + همان نوع معامله + شهر/آدرس/تلفن یکسان)، و ۲) در برابر
ردیف‌های دیگر همان فایل اکسل (اگر خودِ اکسل تکرار داشته باشد). ردیف‌های
تکراری نه با خطا رد می‌شوند نه بی‌صدا دوباره ثبت می‌شوند — در گزارش Import
به‌عنوان «⚠️ تکراری» جدا از «❌ خطا» نشان داده می‌شوند.

**یک باگ واقعی و نسبتاً مهم که در همین تست پیدا و رفع کردم:** وقتی برای اولین
بار این ویژگی را تست کردم، تشخیص تکراری بر اساس تلفن کار نمی‌کرد. دلیلش این
بود که `pandas` وقتی یک ستون اکسل (مثل «تلفن مالک») فقط شامل مقادیر
عددی‌شکل باشد، آن ستون را خودکار به نوع عددی تبدیل می‌کند و **صفر ابتدایی
شماره‌های ایرانی را حذف می‌کند** (مثلاً `09121112233` می‌شود `9121112233`).
این یعنی همین باگ، مستقل از قابلیت تشخیص تکراری، شماره تلفن‌های ثبت‌شده از
طریق Import را هم خراب می‌کرد! با اضافه‌کردن `dtype=str` به `pd.read_excel`
(که همه‌ی ستون‌ها را به‌صورت متن می‌خواند، نه با حدس نوع داده) این مشکل کاملاً
رفع شد. این را با ساخت یک دیتابیس تمیز، وارد کردن یک اکسل واقعی حاوی هم
تکراری‌های بین فایل هم تکراری در برابر دیتابیس، و بررسی این‌که همه‌ی شماره
تلفن‌های نهایی هنوز با صفر شروع می‌شوند، تایید کردم.

**۱۰. لاگ فایل ساختاریافته روی سرور ✅ (انجام شد):**
قبلاً فقط خروجی ترمینال uvicorn بود — اگر سرور شب/آخر هفته کرش می‌کرد، هیچ
سابقه‌ای برای بررسی نمی‌ماند. حالا `app/core/logging_config.py` یک
`RotatingFileHandler` می‌سازد (`server/logs/app.log`، حداکثر ۵ مگابایت هر
فایل، ۵ فایل چرخشی قدیمی = تا ۳۰ مگابایت مجموع) و یک
`@app.exception_handler(Exception)` سراسری اضافه شد: هر خطای پیش‌بینی‌نشده
با traceback کامل در فایل ثبت می‌شود و کلاینت به‌جای جزئیات داخلی سرور، یک
پیام تمیز فارسی می‌گیرد.

**دو نکته‌ی فنی واقعی که فقط با تست مستقیم کشف شدند (نه با خواندن مستندات):**
- لاگر `uvicorn.access` (که لاگ هر درخواست HTTP را می‌سازد) به‌طور پیش‌فرض
  `propagate=False` دارد — یعنی حتی با اضافه‌کردن handler به root logger،
  هیچ لاگ درخواستی به فایل نمی‌رسید. این را فقط با اجرای واقعی سرور و چک
  کردن محتوای فایل لاگ متوجه شدم (نه با فرض قبلی که در کامنت کد نوشته بودم و
  اشتباه از آب درآمد).
- رفع اول باعث شد هر پیام از `uvicorn.error` **دوبار** ثبت شود (یک‌بار مستقیم،
  یک‌بار از طریق propagate به root). با `propagate = False` صریح روی لاگرهای
  uvicorn، این تکرار هم برطرف شد.

**تست واقعی که انجام دادم:** سرور را بالا آوردم، یک درخواست موفق (`/health`)
و یک درخواست ناموفق (لاگین اشتباه) زدم و فایل لاگ را خواندم — هر دو با کد
وضعیت درست و بدون تکرار ثبت شده بودند. جداگانه هم exception handler را با یک
خطای شبیه‌سازی‌شده مستقیم صدا زدم: پاسخ به کلاینت تمیز و فارسی بود، و
traceback کامل خطا در فایل لاگ ثبت شده بود.

**۱۱. اعلان فوریت‌های قرارداد هنگام ورود ✅ (انجام شد):**
قبلاً تب «قراردادهای رو‌به‌اتمام» کاملاً منفعل بود — کاربر باید خودش یادش
می‌ماند بازش کند. حالا بلافاصله بعد از ورود موفق، برنامه از همان endpoint
`GET /properties/renewals` (که از قبل وجود داشت) با یک بازه‌ی کوتاه‌تر و
فوری‌تر (۷ روز، جدا از بازه‌ی معمولیِ ۳۰ روزه‌ی خودِ تب) سؤال می‌کند؛ اگر
نتیجه‌ای بود، یک دیالوگ برجسته (`UrgentRenewalsDialog`) با جدول قراردادهای
فوری و روزهای باقی‌مانده نشان می‌دهد، با دکمه‌ی «مشاهده‌ی همه» که مستقیم به
همان تب سوییچ می‌کند.

**تست واقعی که انجام دادم:** سمت سرور، دو فایل ساختم (یکی ۳ روز، یکی ۲۰ روز
تا پایان قرارداد) و تایید کردم `days=7` فقط اولی را برمی‌گرداند و `days=30`
هر دو را. سمت کلاینت، دیالوگ را با PySide6 واقعی (headless) با داده‌ی نمونه
ساختم و محاسبه‌ی «روز باقی‌مانده» را بررسی کردم (۳ و ۱ روز درست محاسبه شد)،
دکمه‌ی «مشاهده‌ی همه» را هم تست کردم. در آخر یک تست یکپارچه‌ی کامل: با سرور
واقعی لاگین کردم، خودِ `MainWindow` واقعی را ساختم، و تایید کردم
`switch_to_renewals_tab()` دقیقاً به تب درست («قراردادهای رو‌به‌اتمام»،
اندیس ۱) سوییچ می‌کند.

باقی مورد roadmap-v3.md (محدودسازی `/docs` عمومی) باقی مانده است.

**۱۲. محدودسازی مستندات عمومی /docs ✅ (انجام شد — آخرین مورد roadmap-v3.md):**
قبلاً Swagger UI (`/docs`)، ReDoc (`/redoc`) و `openapi.json` بدون نیاز به
هیچ لاگینی روی شبکه‌ی دفتر در دسترس بودند — یعنی هرکسی روی شبکه می‌توانست
ساختار کامل API (اسم هر endpoint، فیلدهای هر مدل) را ببیند. حالا یک تنظیم
`DEBUG` (پیش‌فرض `false`) اضافه شد: در محیط عملیاتی هر سه این آدرس‌ها کاملاً
غیرفعال هستند (۴۰۴)؛ فقط با گذاشتن `DEBUG=true` در `.env` (برای توسعه‌ی
محلی) دوباره در دسترس می‌شوند.

**تست واقعی که انجام دادم:** سرور را یک‌بار با `DEBUG=false` بالا آوردم و
هر سه آدرس (`/docs`, `/redoc`, `/openapi.json`) را چک کردم — هر سه ۴۰۴ دادند
درحالی‌که `/health` عادی کار می‌کرد؛ سپس با تغییر `.env` به `DEBUG=true` و
ری‌استارت سرور، هر سه دوباره ۲۰۰ برگرداندند.
